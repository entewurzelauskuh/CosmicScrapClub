Purpose
=======
This audit reviews the Unity project against the current docs in README.md,
full_architecture.md, cube_fly_spec.md, ROADMAP.md, and the implemented code,
scenes, prefabs, and assets. It is written for a follow-up agent that will
improve the project.

Scope and validation
====================
- Reviewed project documentation, Unity C# scripts, YAML scenes/prefabs,
  ScriptableObject assets, ProjectSettings, package manifest, and git status.
- Queried Unity MCP for the active scene, build settings, loaded scenes, and
  console messages. No game compile/runtime errors were observed in the console;
  the visible warnings/errors were MCP client lifecycle/time-out messages.
- No automated project tests were found under Assets, and no full Unity test run
  was executed.
- This audit intentionally does not modify source code, scenes, prefabs, or
  settings. It adds only this review file.

Executive summary
=================
The project is compact and readable, with a clear build/fly loop and sensible
separation between core model, build mode, flight mode, weapons, UI, and desert
visual work. The ScriptableObject shape/material registry is a good foundation,
the v2 save schema already anticipates ship-class data, and the damage/removal
pipeline is shared cleanly enough to extend.

The main risks are architectural drift rather than low-level code quality:
GameData is doing too much as global mutable state, build and flight each rebuild
their own view of the construct, runtime UI is split across many self-bootstrapped
canvases, and documentation has fallen behind the implemented state. The most
important behavioral risks are the build-mode connectivity cleanup ignoring
face-valid shape rules, flight Rigidbody mass becoming stale after cube death,
and projectile collision sweeps using a small fixed hit buffer that can miss real
targets in dense/self-overlapping cases.

High priority findings
======================

1. Build cleanup can leave invalidly attached structures after deletion.

Files:
- Assets/Scripts/Build/BuildManager.cs:581-595
- Assets/Scripts/Core/GameData.cs:158-188

Build placement correctly validates attachments with symmetric face validity in
GameData.IsValidAttachment. However, BuildManager.RemoveDanglingCubes performs a
raw six-neighbor flood fill over occupied cells and does not reuse the same
face-aware attachment rule. That means a construct containing slopes, pyramids,
cylinders, thrusters, or future one-sided shapes can be considered connected
through a cell face that the involved ShapeDefinition says is not attachable.

Impact:
- Deleting a true connector can leave orphaned chunks because the cleanup graph
  is more permissive than the placement graph.
- Future shapes with directional faces will make this easier to reproduce.
- Build-mode validity, save state, and visual shape constraints can diverge.

Recommended fix:
- Extract a shared connectivity helper, for example
  GameData.HasValidConnection(Vector3Int a, Vector3Int b), that checks occupied
  cells and both shapes' world-face validity.
- Use that helper in placement validation, dangling-cube cleanup, and any future
  flight detachment logic.
- Add EditMode tests for cube-to-cube, cube-to-slope, slope-to-slope,
  cylinder/thruster face validity, and deletion of a connector.

2. Ship Rigidbody mass and inertia are stale after cube destruction in flight.

Files:
- Assets/Scripts/Fly/FlyController.cs:157-159
- Assets/Scripts/Fly/CubeDamage.cs:73-78
- Assets/Scripts/Fly/CubeDeath.cs:52-55

FlyController computes Rigidbody mass once when the construct is built. A code
comment already notes that mass is not updated when cubes are destroyed. Cube
death removes GameData entries and destroys objects, but the Rigidbody mass,
center of mass, inertia tensor, movement tuning, weapon lists, and HUD-visible
state are not recomputed as one coherent construct update.

Impact:
- Destroyed cubes still affect flight mass and inertia for the rest of the run.
- Movement, collision, and future thruster boost behavior can feel inconsistent.
- Weapon and HUD systems can drift unless each subsystem handles destruction on
  its own.

Recommended fix:
- Introduce a flight-side ConstructRuntimeState or ConstructBody service that
  owns live cube membership, mass properties, center of mass, weapon mounts, and
  events such as CubeDestroyed.
- Recompute Rigidbody.mass and related mass properties after cube death.
- Consider detaching or destroying disconnected chunks with the same face-valid
  graph helper proposed for build mode.
- Add PlayMode coverage for destroying a cube and verifying Rigidbody mass, HP
  display, weapon list, and GameData state remain aligned.

3. Projectile sweeps can miss valid targets when the small hit buffer fills.

Files:
- Assets/Scripts/Fly/ProjectileHit.cs:21
- Assets/Scripts/Fly/ProjectileHit.cs:34-58

ProjectileHit uses Physics.RaycastNonAlloc with a static RaycastHit[8] buffer,
sorts only the returned hits, and filters self hits after the raycast. If more
than eight colliders are along the path, especially colliders belonging to the
player construct, the buffer can fill before the first valid non-self target is
included.

Impact:
- Fast bullets or rockets may pass through enemies/terrain in dense scenes.
- The issue becomes more likely as constructs grow and projectile origins are
  near or inside self colliders.

Recommended fix:
- Prefer layer/collision filtering that excludes self before the raycast where
  possible.
- Increase the buffer and detect saturation, or use RaycastAll for this low
  projectile count and sort/filter reliably.
- Add a regression test with more than eight self colliders in front of a valid
  target.

5. No project tests or assembly definition boundaries were found.

Files:
- Assets/Scripts

The project currently has no Assets-side test assemblies and no asmdef files for
runtime/editor/test separation. Everything compiles into default assemblies.

Impact:
- Regression risk is high for GameData rules, save migration, shape registry
  validation, damage, and flight rebuild behavior.
- Follow-up agents have no fast safety net.
- Editor-only code and runtime code are harder to separate as the project grows.

Recommended fix:
- Add asmdefs such as CubeFly.Runtime, CubeFly.Editor, CubeFly.Tests.EditMode,
  and CubeFly.Tests.PlayMode.
- Start with small deterministic EditMode tests:
  - GameData placement and face-valid attachment.
  - ConstructSave v1/v2 load and migration behavior.
  - SaveManager metadata handling.
  - ShapeRegistry uniqueness and asset validation.
  - Build mass-cap calculations by ship class.
- Add PlayMode smoke tests:
  - MainMenu -> HangarSelect -> BuildScene -> FlyScene scene flow.
  - Damage removes cube and updates live construct state.
  - GameOver appears when alpha cube dies.

6. GameData is a convenient facade, but it is becoming a global domain service.

Files:
- Assets/Scripts/Core/GameData.cs
- Assets/Scripts/Build/BuildManager.cs
- Assets/Scripts/Fly/FlyController.cs

GameData owns active slot, active ship class, placed cells, placed-by-cell
lookup, save conversion, load behavior, and attachment validation. This is still
manageable at current size, but new systems such as thruster boost, shields,
power, inventory, enemies, and persistent progression will make this static
mutable state harder to reason about.

Impact:
- Systems mutate project state directly without lifecycle ownership.
- Scene transitions rely on static state being correct.
- Runtime flight damage edits the same state used for build/save semantics.

Recommended fix:
- Keep GameData as a compatibility facade if desired, but extract a
  ConstructModel with explicit methods/events for placement, removal, load,
  save, and validation.
- Separate "design-time construct" from "flight runtime construct" so combat
  damage does not accidentally mutate the saved build unless that is explicitly
  intended.
- Add events such as CellAdded, CellRemoved, ConstructLoaded, ShipClassChanged,
  and ActiveSlotChanged.

7. BuildToolbarController remains a large UI/controller monolith.

Files:
- Assets/Scripts/Build/BuildToolbarController.cs
- Assets/Scripts/Build/CategoryFlyout.cs
- Assets/Scripts/Build/BuildShipClassController.cs

The CategoryFlyout extraction is a good step, but BuildToolbarController still
handles UI creation, input polling, selected shape state, material selection,
preview details, flyout orchestration, and Fly button state. It is over 900
lines and still has comments that describe the older "weapons today; utilities
later" state.

Impact:
- Adding thruster boost UI, filters, tooltips, gamepad support, or richer shape
  categories will increase coupling.
- Shortcut behavior is mixed into view code instead of input/action mapping.

Recommended fix:
- Split into a BuildSelectionModel, ShapePaletteView, MaterialPaletteView,
  CategoryFlyoutView, FlyButtonPresenter, and small input adapter.
- Prefer explicit events over direct cross-calls among UI widgets.
- Update comments and names from weapon-specific terminology to coupled-material
  or category terminology where the code now supports Utility shapes too.

8. Runtime UI is scattered across many canvases and self-bootstrapped objects.

Files:
- Assets/Scripts/Core/UIManager.cs
- Assets/Scripts/Core/PauseMenu.cs
- Assets/Scripts/Core/GameOverMenu.cs
- Assets/Scripts/Build/BuildToolbarController.cs

The project creates multiple canvases in code: corner UI, pause menu, game over,
build toolbar, ship class dropdown, crosshair, weapon toolbar, speed HUD, and HP
HUD. This is pragmatic, but sorting, EventSystem ownership, raycast behavior,
and visual consistency will become harder to manage.

Impact:
- Harder visual QA and harder prefab/scene inspection.
- Multiple canvases can cause ordering and input surprises.
- UI styling changes require edits across many scripts.

Recommended fix:
- Introduce a scene HUD root per mode, or a small UI composition prefab with
  mode-specific panels.
- Keep UIStyle if code-built UI is preferred, but centralize canvas creation,
  sorting order, scale settings, fonts, colors, and EventSystem ownership.
- Move stable screen layouts into prefabs or UI Toolkit if the project is likely
  to grow.

9. BuildScene has likely stale serialized UI values for the rotate hint.

Files:

- Assets/Scripts/Build/BuildToolbarController.cs:40-43

The script default hint font size is 18 and hint size is 220x32. The BuildScene

Impact:

10. Shape/material asset validation is currently manual.

Files:
- Assets/Shapes/ShapeRegistry.asset
- Assets/Shapes/ShapeUtilityThruster.asset
- Assets/Prefabs/PlacedThruster.prefab
- Assets/Scripts/Core/ShapeDefinition.cs
- Assets/Scripts/Core/MaterialDefinition.cs

The registry now includes Armour, Weapon, and Utility shapes. Non-armour shapes
can use coupled materials through ShapeDefinition.coupledMaterial. This is a
good pattern, but there is no automated validation for required prefab
components, unique names, layer/tag assignments, face flags, coupled material
requirements, or material stats.

Impact:
- A missing CubeStats, collider, PlacedCubeData, layer, or material assignment
  can break placement, mass, save/load, combat, or preview behavior at runtime.
- Utility shapes are especially easy to misconfigure because they are newer.

Recommended fix:
- Add an editor validation tool and EditMode tests for the full registry:
  - Unique shape displayName.
  - Every shape has a prefab with collider, renderer/mesh, CubeStats,
    PlacedCubeData, and expected layer.
  - Armour shapes have materialOptions.
  - Non-armour shapes either have a coupledMaterial or explicitly document why
    they do not.
  - Face-valid flags are not all false unless intentionally unplaceable.

Architecture recommendations
============================

1. Create a shared construct domain layer.

Introduce a ConstructModel that is independent of Unity scene objects and owns:
- Cells and placed shape/material entries.
- Face-aware connectivity and attachment rules.
- Mass/stat aggregation.
- Save/load conversion and version migration.
- Events for add/remove/load/class changes.

Build mode should manipulate ConstructModel. Flight mode should instantiate a
runtime body from a snapshot of ConstructModel. This reduces the current tension
where GameData is both the build/save source and the mutable combat state.

2. Separate design-time save state from flight damage state.

Decide whether damage in FlyScene should persist back to the saved construct.
Currently CubeDamage removes cells from GameData during flight. If that is
intended, make it explicit in a ConstructDamageState and save policy. If not,
flight should operate on a runtime copy and leave the saved design untouched.

3. Add a construct validation pipeline.

Create a single editor command and test suite that validates:
- ShapeRegistry.
- Materials.
- Required tags/layers.
- Build settings scenes.
- Required scene bootstrap objects.
- Save files/migrations.
- Prefab components and layers.

This will pay off quickly as new shape categories and systems are added.

4. Implement thruster boost as a system, not a FlyController special case.

The current thruster asset is placeable and inert. For the next phase, add a
ThrusterBehavior/ThrusterMount plus a ConstructThrusterSystem that scans live
thrusters, computes directional contribution, owns boost resource/cooldown, and
publishes values to HUD/audio/VFX. FlyController should consume a movement
modifier or force contribution rather than know all thruster details.

Recommended pieces:
- ThrusterMount on PlacedThruster prefab.
- ThrusterRegistry/scan during flight construct build.
- Boost state machine: idle, active, depleted, cooldown.
- HUD indicator integrated with the flight HUD root.
- Tests for no thrusters, one thruster, multiple opposing thrusters, destroyed
  thruster, and saved v2 construct load.

5. Centralize input ownership.

FlyController, FlyCamera, and FlyShootingController each create their own
CubeFlyInputActions instance. This works, but it spreads input lifecycle and
rebinding concerns across systems. A small PlayerInputService or scene-level
input owner would make gamepad support, pause behavior, rebinding, and UI focus
rules cleaner.

6. Consolidate runtime HUD composition.

Use one HUD root per mode or a shared UI bootstrapper that creates and owns the
mode-specific panels. Keep each indicator as a small component, but avoid every
indicator creating its own canvas and styling rules. This will simplify sorting,
screen scaling, theming, and screenshot verification.

7. Introduce a damage/hit context model before adding more combat systems.

CubeDamage, ProjectileHit, Bullet, Rocket, FlyCrashHandler, and WeaponBehavior
are currently straightforward. Before adding shields, resistances, splash
falloff, enemies, or friendly fire, introduce a DamageRequest/HitContext model
with fields such as source, target, amount, type, impulse, point, normal, and
flags. That keeps projectile and collision damage from diverging.

8. Treat docs as part of the build contract.

The docs are useful, but they should be explicitly marked as either:
- Current behavior.
- Accepted next-step specification.
- Historical reference.

For agent-driven development, this distinction matters. A short docs index in
README.md would prevent future agents from following stale roadmap text over
implemented code.

Suggested implementation order for a follow-up agent
====================================================

1. Add project tests and asmdefs.
Start with GameData/ConstructModel behavior and registry validation. This gives
future refactors a safety net.

2. Extract face-aware construct connectivity.
Use it for placement, build dangling cleanup, and later flight detachment.

3. Fix flight runtime state after cube destruction.
Recompute mass/inertia/HUD/weapon membership through one runtime construct
service. Decide whether flight damage persists to saved design state.

4. Repair repository hygiene.
Update .gitignore, decide embedded-vs-package MCP strategy, and align README
with the actual repo state.

5. Update docs to match current implementation.
Correct logging, save v2, ship classes, utility/thruster state, and roadmap
status.

6. Refactor build UI incrementally.
Extract selection state and palette views from BuildToolbarController without
changing behavior.

7. Implement thruster boost using a dedicated system.
Build on the new construct/runtime model rather than adding more direct logic to
FlyController.

Most important regression tests to add
======================================

- Placing a slope/pyramid/cylinder/thruster respects both cells' valid faces.
- Removing a connector deletes every cell no longer face-valid connected to the
  alpha cube.
- Loading a v1 save still succeeds and loading a v2 save preserves shipClass.
- ShapeRegistry rejects duplicate displayName values and invalid prefabs.
- Build mass limit changes when switching Allrounder, Tank, and Scout.
- FlyScene Rigidbody mass updates after a placed cube is destroyed.
- ProjectileHit still hits the nearest non-self target when more than eight
  self colliders are in front of it.
- MainMenu, HangarSelect, BuildScene, and FlyScene all load without missing
  bootstrap UI or required references.

Closing note
============
The project is in a good state for its size: it has clear gameplay intent, a
reasonable registry-driven content model, and focused scripts that mostly do
what their names promise. The next improvement step should be to put a small,
tested construct domain layer underneath the existing scenes. That will make
thrusters, more weapons, enemies, shields, and persistent progression much less
fragile to add.
